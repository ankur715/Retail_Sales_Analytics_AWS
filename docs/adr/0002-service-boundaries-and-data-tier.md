# ADR 0002: API versioning, a Redis answer cache, idempotent retries and a gRPC SQL service

- Status: accepted
- Date: 2026-10-13
- Milestone: 2 (service architecture and data tier)

## Context

ADR 0001 measured where the chatbot's time goes: the three sequential LLM calls are about 99%
of each request. The cheapest request is the one that never reaches the model. The chatbot
already cached answers, but only in process memory, for 15 minutes. The problems with that:

- A restart lost every cached answer.
- Two replicas wouldn't share answers.
- A new data load didn't retire old answers.

Clients that retried a slow request (a timeout, a double click) paid for the whole pipeline
again. The API had no version, so any change would break the web page and the load test at
once. And the step most likely to change on its own, writing SQL, was tangled into the web
handler.

## Decisions

**1. Versioned routes: `/v1/chat`, `/v1/health`. `/api/*` stays.** The old routes run the
same handler, are marked `deprecated` in OpenAPI, and send `Deprecation: true` plus a
`Link: </v1/...>; rel="successor-version"` header. The web page and k6 moved to `/v1`. The old
routes can go once their traffic in `chatbot_requests_total{route="/api/chat"}` stays at zero.

**2. The answer cache lives in Redis and is keyed by data version.**
- Key: `chat:answer:<version>:<sha256 of the normalized question>`, 15-minute TTL.
- Version: `MAX(last_successful_load_at)` from `chat.v_data_freshness`, the latest successful
  load. The milestone plan said "invalidate on each new `load_id`", but the read-only
  `chat_reader` can only see the `chat` schema, which exposes load *times*, not load IDs. A
  new load changes the version, so older answers stop matching and simply expire. No scan or
  delete is needed.
- Each process looks the version up at most once a minute. An answer can therefore trail a
  load by up to 60 s; `cache.invalidate()` makes that instant, and milestone 3's
  `load_completed` event will call it.
- The version is read once, at the start of a request, and the answer is filed under it. An
  answer computed while a load lands is filed under the old data it came from.
- Failure modes:
  - Redis down: the request runs uncached; it does not fail.
  - Database down: the last known version is reused, so cached answers keep being served.
  - Both are counted in `chatbot_store_errors_total{op}`.

**3. `Idempotency-Key` on POST.**

| Case | Response |
|---|---|
| First request | Claims the key (2-minute "processing" record), runs, stores the 200 for 24 h |
| Same key, same body | The stored response, `Idempotent-Replayed: true` |
| Same key while the first is running | 409 |
| Same key, different body | 422 |
| First run fails (503, crash) | The key is released, so the retry runs for real |

Records are stored under a hash of the key, never the key itself. If Redis is down, the
request runs without idempotency ("fail open"). For a read-only chatbot, a duplicate run
costs a few model calls, while refusing service would cost the answer. A payments API would
choose the other way.

**4. SQL generation is a gRPC service (`sqlgen/`).**
- The boundary is the `write_sql` step only, with the same signature as before. It's the step
  with the most independent future: prompt work, a different or self-hosted model, RAG over
  the catalog (milestone 5). It needs no database access, so the service holds no
  credentials.
- `route`, `summarize` and the query stay in the web app. Splitting all of them would put a
  network hop between every step, for no isolation benefit yet.
- LLM failures become gRPC status codes, and the client turns them back into the same
  `LLMUnavailable` kinds, so the user still gets a clear 503:

  | Failure | gRPC status |
  |---|---|
  | busy | `UNAVAILABLE` |
  | quota | `RESOURCE_EXHAUSTED` |
  | config | `FAILED_PRECONDITION` |
  | declined | `PERMISSION_DENIED` |

  A transport failure or timeout also becomes "busy". Bugs (`INVALID_ARGUMENT`, `INTERNAL`)
  stay 500s.
- With `SQLGEN_ADDR` unset, the client calls the function in-process. Tests, CI and a laptop
  `uvicorn` need no second process.
- The stubs are committed. CI regenerates them and fails if they differ.
- `grpcio-tools` is pinned to the version Airflow's constraint file allows, because stubs
  generated by a newer version require a newer protobuf than Airflow permits.

**5. A migration-safety check in CI** (`scripts/check_migrations.py`).
- **History:** applied migrations are never edited, deleted or renamed, and new files are
  numbered after the base branch's latest. `etl.migrate` already refuses an edited file, but
  only at deploy time.
- **Content:** in new migrations, it flags statements that lose data or break readers while
  the old code still runs: drops, truncates, unbounded `DELETE`/`UPDATE`, renames, column
  type changes, and `NOT NULL` columns added without a default.
- **Exceptions:** an exception must be written into the migration, with a reason, as
  `-- migration-safety: allow <rule>: <reason>`, so the reviewer sees it in the diff.

## Measurements (2026-10-13, Codespace, fake LLM ~800 ms per call, 10x = 20 users, 4 min)

70% of questions repeated from a pool of 40; 30% were unique (always miss). Every request
carried an `Idempotency-Key`, and 10% were sent twice.

| | Milestone 1 (cache bypassed) | Milestone 2 (cache on) |
|---|---|---|
| Throughput | 7.99 req/s | **28.7 req/s** (3.6x, same 20 users) |
| Failed | 0% | 0% (7,109 requests) |
| Cache hit ratio | n/a | 69% (4,500 hits, 1,990 misses) |
| Hit latency p50 / p95 / p99 (k6) | n/a | **3.1 / 11.7 / 24.7 ms** |
| Miss latency p50 / p95 / p99 (k6) | 2.17 / 5.13 / 7.10 s | 2.16 / 5.12 / 6.85 s |
| Retries replayed | n/a | 622 of 622; a 1-minute rerun checked 186 of 186 bodies byte-identical |

- **Cache hits:** a hit is about **700 times faster** than a miss at the median. Hits don't
  queue behind the model, so the same 20 users got 3.6 times the throughput.
- **gRPC hop:** it added a median of **1.9 ms** (p95 2.5 ms) per request, about 0.2% of the
  `write_sql` call it wraps. Miss latency is unchanged from milestone 1.
- **Traces:** they cross the boundary, `rpc.sqlgen.WriteSql` in the chatbot and then
  `llm.write_sql` in `sqlgen`, so ADR 0001's per-step view still holds.

## Consequences

- **Hit ratio decides cost.** Real traffic is unlikely to repeat 70% of questions word for
  word. Normalizing only case and spacing is deliberately conservative: a looser match
  (embeddings) could return the wrong numbers. That belongs to milestone 5, with an eval to
  check it.
- **The cache can be wrong for up to 60 s after a load.** That's acceptable for weekly data.
  Milestone 3's event makes it immediate.
- **Redis is now on the request path,** with 250 ms timeouts and a fallback for every
  failure. Milestone 3's chaos tests should kill it and confirm the chatbot keeps answering.
- **Two processes to deploy instead of one.** The Compose stack runs both from one image;
  milestone 3 gives them separate Kubernetes deployments.
- **Jaeger now needs more memory per trace** (about 12 spans across two services). Its
  in-memory cap went from 20k to 8k traces after it was killed for running out of memory.

## Alternatives considered

- **Header or media-type versioning** (`Accept: application/vnd...v1`): it's invisible in
  logs, in the route label on metrics, and in Swagger's grouping. Path versioning is plainer.
- **Deleting cache keys on each load** instead of versioning them: that needs a scan, and a
  missed delete serves stale data forever. With versioned keys, stale data can never match.
- **Idempotency through the cache alone:** the cache can't tell a retry from a new request,
  or detect a reused key with a different body, and a cache hit still reruns the handler.
  Idempotency is a contract with the client; caching is an optimization.
- **REST for the internal call:** it would work. gRPC gives a typed contract
  (`sqlgen.proto`), generated clients and deadlines, which matter more as more services are
  split out.
