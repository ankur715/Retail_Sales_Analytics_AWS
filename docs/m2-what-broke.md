# Milestone 2: what broke and why

| # | What broke | Why | Fix |
|---|---|---|---|
| 1 | Installing the gRPC instrumentation left the venv with mismatched OpenTelemetry packages (`pip check` failed) | pip pulled the newest `opentelemetry-instrumentation-grpc`, which required a newer `opentelemetry-api` than the pinned SDK | Pinned the instrumentation to the SDK's matching release (0.65b0). Lesson: run `pip check` after every install. |
| 2 | The first generated gRPC stubs would have broken the Airflow CI job | `grpcio-tools` 1.83 writes stubs that need protobuf ≥ 7.35, but Airflow's constraint file pins protobuf 6.33.6 (and grpcio-tools 1.81.1) | Generated the stubs with grpcio-tools 1.81.1, pinned in `requirements.txt`. Older stubs load on newer protobuf runtimes, not the other way round. |
| 3 | `import chatbot.app` failed on the laptop: no `prometheus_client` | Milestone 1's telemetry packages had only ever been installed in the Codespace, so the laptop venv was behind `requirements.txt` | `pip install -r requirements.txt` locally. Check with `pip install --dry-run` before assuming a venv is current. |
| 4 | The test for a non-ASCII `Idempotency-Key` crashed inside the HTTP client, not the server | httpx refuses to encode non-ASCII header strings | The test sends raw bytes, which is what a misbehaving client would actually put on the wire |
| 5 | `/v1/health` returned 503 in a test | `model_name()` raises when `LLM_PROVIDER=none` (the test default). `/api/health` has always behaved this way. | The test sets the fake provider. Left as is: with no LLM the service is degraded, and 503 says so. |
| 6 | The first cache-mode load-test design would have produced a useless hit-vs-miss chart | With a fixed pool of 40 questions, all of them are cached within a minute, so the "miss" line disappears | 30% of questions are unique (always miss) and 70% repeat, so both lines stay visible for the whole run |
| 7 | k6 reported all 622 idempotent retries as "different body", although every one was replayed | The check compared `JSON.stringify(res.json())` after the script had already called `res.json("cached")` on the same response. In k6 that re-parse isn't a reliable comparison. Fetching both bodies with curl showed them byte-identical. | Compare the raw bodies (`r.body === res.body`). A 1-minute rerun passed 186 of 186. Lesson: when a check fails 100% of the time, suspect the check first. |
| 8 | Jaeger was killed for running out of memory (exit 137) right after the load test | Its 384 MB limit held 20,000 traces in milestone 1. Traces now have about 12 spans across two services (cache, data version, gRPC client and server), and at 28 req/s the cap was reached in minutes. | `--memory.max-traces=8000` |
| 9 | The Grafana screenshot timed out waiting for the new panels | Grafana 11 renders only the panels inside the viewport, and the milestone 2 row sat below the fold of a 900 px page | That shot uses a 1500 px tall page |
| 10 | `gh codespace cp` couldn't find the screenshots | Without `-e` (`--expand`), the same absolute path failed with "No such file"; with it, the copy worked. Milestone 1 copied files the same way, so this is the command to reuse. | `gh codespace cp -e -c <name> 'remote:/workspaces/...' pics/` |
| 11 | The old in-process cache's 15-minute TTL was the only invalidation | It didn't know when new data arrived, so a fresh load could keep serving stale answers for 15 minutes | Cache keys include the data version (latest successful load). A cached answer can now trail a load by at most the 60-second version lookup interval. |
