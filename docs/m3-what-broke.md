# Milestone 3: what broke and why

| # | What broke | Why | Fix |
|---|---|---|---|
| 1 | The `SqlgenDown` promtool test failed in CI: the alert had no `job` label | `absent()` copies labels only from a plain selector. `absent(up{job="sqlgen"} == 1)` wraps a comparison, so the result has no labels, and alert routing couldn't tell which service was down. | Set `job` explicitly on both "down" alerts. The rule unit tests caught this before any alert was routed. |
| 2 | Redpanda crash-looped on its first start in kind | `--set redpanda.auto_create_topics_enabled=true` isn't a `rpk redpanda start` flag. rpk passed it through to the broker, which rejected it. | Removed it; dev-container mode already auto-creates topics. Argo CD then deployed the fix from git without a single `kubectl` command. |
| 3 | Each chatbot replica counted a "broker error" at startup, enough to trip `LoadEventsFailing` | The listener subscribed before the first `load_completed` had created the topic, and every broker error went in one bucket | A missing topic is counted as `topic_pending`, which the alert ignores. Real broker errors still count. |
| 4 | The laptop's `pytest`, `pip` and `uvicorn` stopped working mid-milestone, and one commit went in with the suite not yet run | The project folder was renamed. A venv's launcher scripts hard-code the absolute path of its Python. | Rewrote the 48 launchers to the new path, then ran the suite (198 passed). Lesson: run tests through `.venv/bin/python -m pytest` and read the output before committing. |
| 5 | Without changes, a database outage would have hung every chat request for 35 s or more | The chatbot shared the ETL's connection helper: 4 attempts, 30 s connect timeout, 5/10/20 s backoff. That's right for waking Redshift Serverless, wrong for a waiting person. | The chatbot passes its own limits: 2 attempts and 10 s by default; 1 attempt and 3 s in kind against the local copy. |
| 6 | Without changes, a dead database would have triggered a pointless "repair" call to the model | The repair loop caught every exception, including connection failures, and asked the model to fix SQL that was fine | Connection failures are `DatabaseUnavailable`: no repair round, straight to the stale fallback or a clear 503 |
| 7 | Without changes, the chaos test's own traffic would have reported outages users never see | `kubectl port-forward svc/...` pins one pod. Kill that pod and the forward dies, though the Service would have routed around it. | The traffic generator runs inside the cluster as a pod and goes through the chatbot Service, like real clients |
| 8 | The first "LLM errors 50%" experiment reported 0 errors, which is impossible | Argo CD undid it. A pushed commit that changed no manifests hadn't been synced yet. When the experiment made the app OutOfSync, automated sync was allowed to apply that newer commit, resetting the error rate to 0 within a second. `selfHeal: false` only stops re-applying a commit already synced. | `chaos/run.py` freezes automated sync during experiments and always restores it (each cleanup step runs on its own, so one failure can't leave Argo frozen) |
| 9 | After every sqlgen pod was replaced, uncached questions kept failing for 20-45 s although sqlgen was back in 2 s | My first diagnosis was CoreDNS's 30 s cache: with a headless Service and client-side `round_robin`, the chatbot finds pods through DNS. Moving sqlgen behind a ClusterIP Service didn't fix it; failures still ran about 20 s past recovery. The real cause: gRPC's `min_reconnect_backoff` (20 s by default) is also its connect timeout. Right after a pod dies, a connect can go to its vanished IP and hang silently that whole time, and every call fails meanwhile. | 1 s connect timeout and 1 s max backoff in `sqlgen/client.py`. The rerun had 3 brief 503s, then 47 of 47 requests succeeded. sqlgen stays behind the ClusterIP, which keeps DNS caching out of failover; the server ages connections out after 30 s so clients spread across pods. Lesson: a fix that "should" work isn't confirmed until the experiment reruns clean. |
| 10 | The chaos traffic only ever reached one of the two chatbot pods | Each worker reused a keep-alive connection, and Kubernetes balances connections, not requests | One connection per request in `chaos/traffic.py`, so both replicas are tested |
| 11 | sqlgen crash-looped right after its Service was renamed to `sqlgen` | Kubernetes injects Docker-link env vars for every Service, including `SQLGEN_PORT=tcp://10.96.x.x:50051`. The server reads `SQLGEN_PORT` for its own port and tried to bind `0.0.0.0:tcp://...`. | `enableServiceLinks: false` on every pod. `POSTGRES_PORT` and `REDIS_PORT` were being injected too; they just hadn't collided yet. |
