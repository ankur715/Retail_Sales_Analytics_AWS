# Milestone 5: what broke and why

| # | What broke | Why | Fix |
|---|---|---|---|
| 1 | **The SQL guard let functions through**: `pg_read_file('/etc/passwd')`, `pg_sleep(60)`, `current_user`, `version()` | The guard checked statements and tables, never functions. The read-only database user would have refused the file read, but `pg_sleep` could tie up the database for the 30 s timeout, and the others leak server details. | Found by running the attack corpus against the guard before writing its expected results. Functions sqlglot doesn't recognise are refused, as are ones that reveal the session or server. The 24 example queries and all eval reference SQL still pass. |
| 2 | **`docker compose --profile app up` failed for everyone since milestone 4** ("required variable KEYCLOAK_ADMIN_PASSWORD is missing") | The auth services used `${VAR:?}` guards to force `deploy/auth/up.sh`. Compose checks every service's variables whatever profile is selected, so the guards broke the app, obs and load profiles too. Milestone 4 only ever started the stack through `up.sh`. | Empty defaults (`up.sh` always sets real values), and a CI step that renders the compose file for every profile with no secrets set |
| 3 | The read-only user couldn't use the vector index: `type "vector" does not exist` | pgvector installed into `public`, and milestone 1's role setup revoked everyone's access to `public` (a good default) | Install pgvector into its own `extensions` schema and grant the reader USAGE on just that schema; index connections set their search path. Caught by the new `ai-integration` CI job against real Postgres. |
| 4 | The chatbot image would have crashed at startup with `No module named 'rag'` | The chatbot now imports the `rag` package, but the Dockerfile copies packages one by one and `rag/` wasn't added. The unit tests run from source, so they couldn't see it. | `COPY rag/ rag/`, plus a test that parses every module the services import and fails if a local package isn't copied into the image |
| 5 | `rich` was missing from `requirements.txt` | The eval and the screenshot scripts use it, but it was only ever installed by hand. The same class of bug as PyJWT in milestone 4; this time CI caught it before any deploy. | Added to `requirements.txt` |
| 6 | The eval would have under-counted cost: only the judge's calls, not the chatbot's | `evaluate()` tracks usage around `answer()`, which opens its own tracker; nested trackers didn't roll up | Nested tracking adds into the enclosing total (tested) |
| 7 | A cross-process gap: the cost of SQL generation was invisible to the chatbot | `write_sql` runs in the sqlgen service, so its tokens were counted in that process only | The gRPC reply carries the call count, tokens and cost; the chatbot adds them to the question's total |
| 8 | The integration test expected the fake model to refuse an off-topic question | The fake model routes every question by keyword, so it always "answers". The eval correctly scored that as a failure. | The test now asserts the eval *catches* it, while the brand-access question passes whatever the model does |
| 9 | Pulling in the Codespace silently did nothing, and the next steps ran on old code | Screenshots committed from the laptop also existed as untracked files in the Codespace, so `git pull -q` refused to overwrite them, and `-q` hid the error | Remove the duplicates, then pull. Lesson: check `git log -1` after every pull in a script, and never pull with `-q` and no check. |
